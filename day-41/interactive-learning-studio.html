MODULE 01 / FOUNDATIONS

Arrays — Contiguous Memory, Instant Access

An array is a fixed-layout block of memory where elements sit back-to-back, each one reachable by an index. The defining trait isn't "a list of things" — plenty of structures are that — it's contiguity: because every element is the same size and they sit next to each other, the computer can jump straight to any slot using pure arithmetic.

Analogy
Think of an array like a row of numbered lockers in a school hallway. If you know it's locker #12, you walk straight there — you don't open lockers 1 through 11 first. That's exactly how array indexing works: address = base_address + (index × element_size).

Notice the address jumps by exactly 4 bytes each slot — that fixed jump is what makes arr[i] a single calculation instead of a search.

Reading, writing, and the cost of resizing

Reading (arr[i]) and writing (arr[i] = x) are both O(1) — constant time — because of that address arithmetic. But arrays have a size baked in at creation. Inserting or deleting in the middle forces every following element to shift, which is O(n). This is the single most important trade-off to internalize about arrays.

// JavaScript — arrays are dynamic under the hood, but the cost pattern still applies
const temps = [72, 75, 68, 80, 77];
temps[2] = 70;              // O(1) write — direct index
temps.push(90);             // O(1) amortized — append at end
temps.splice(1, 0, 100);    // O(n) — everything after index 1 shifts right

Common misconception
"Arrays and lists are the same thing." In many languages (Python's list, JS arrays) the built-in type is a dynamic array that resizes and hides the resizing cost from you. The underlying contiguous-memory behavior is still there — that's why list.insert(0, x) is still O(n) in Python.
Common misconception
"Appending is always O(1)." It's amortized O(1) — most pushes are cheap, but occasionally the array is full and must be copied into a bigger block, which is O(n) for that one call. Averaged over many pushes, it works out to O(1).

Key takeaways

  • Contiguous memory + fixed element size = O(1) indexed access
  • Insert/delete in the middle or front is O(n) due to shifting
  • Dynamic arrays (JS array, Python list) hide resizing but keep the same shift cost

Module 1 Check — Arrays

1. Why is arr[i] O(1) instead of requiring a search?
Correct answer: "The address is computed directly..." — contiguous, fixed-size storage means the address is pure arithmetic, no searching needed.
2. Inserting an element at index 0 of a 10,000-element array is:
Correct answer: O(n) — all 10,000 existing elements must shift one slot to the right to make room.
3. What does "amortized O(1)" mean for array push?
Correct answer: "Most pushes are O(1)..." — the rare full-copy resize is expensive, but spread across many pushes the average cost stays constant.
4. Which best describes what makes something an "array" rather than just "a list of values"?
Correct answer: "Its elements are stored contiguously..." — contiguity is the defining structural property, not the size limits or data type.
MODULE 02 / STACKS

Stacks — Last In, First Out

A stack restricts access to one end only. You can push onto the top, pop off the top, or peek at the top — nothing else is directly reachable. That single restriction is the whole point: it models any process where the most recent thing must be undone or finished first.

Analogy
A stack of dinner plates. You add a clean plate on top of the pile, and you take plates off the top too — the plate at the bottom won't be touched until every plate above it is gone. That's LIFO: Last In, First Out.
Interactive stack — push/pop and watch it build vertically

The call stack: stacks running your code right now

Every time a function calls another function, the runtime pushes a new "frame" onto the call stack. When a function returns, its frame pops off. Recurse too deep with no base case and you exhaust the stack — that's exactly what a "Maximum call stack size exceeded" error means.

function factorial(n) {
  if (n <= 1) return 1;      // base case: frame returns, pops off
  return n * factorial(n - 1); // each call pushes a new frame
}
factorial(4); // stack grows: f(4)→f(3)→f(2)→f(1), then unwinds/pops back down

Common misconception
"A stack is just an array with extra steps." Structurally in many implementations it is built on an array — but the value of a stack is the discipline of only touching the top. That restriction is what makes reasoning about undo/recursion/parsing correctness tractable.

Key takeaways

  • LIFO: last element pushed is the first popped
  • push/pop/peek are all O(1)
  • Powers recursion (call stack), undo history, and matching/parsing problems

Module 2 Check — Stacks

1. What does LIFO stand for?
Correct answer: "Last In, First Out" — the most recently pushed item is always the next one popped.
2. After push(5), push(9), pop(), what does peek() return?
Correct answer: 5 — push(5) then push(9) puts 9 on top; pop() removes 9, leaving 5 on top.
3. What causes a "stack overflow" in recursion?
Correct answer: nested calls pushing frames without returning (popping) — usually a missing or broken base case.
4. Which problem is a textbook fit for a stack?
Correct answer: balanced brackets — you push opening brackets and pop-match them against closers, which is a direct LIFO fit.
MODULE 03 / QUEUES

Queues — First In, First Out

A queue also restricts access, but at two ends: you enqueue at the back and dequeue from the front. Whoever got in line first gets served first — FIFO.

Analogy
A checkout line at a store. New customers join the back; the cashier serves whoever's at the front. Nobody gets served out of order just because they're impatient — that fairness guarantee is exactly what a queue enforces in code.
Interactive queue — enqueue/dequeue

The naive-array pitfall — and the circular queue fix

If you implement a queue by dequeuing from index 0 of a plain array, every dequeue shifts everything left — that's O(n), defeating the purpose. The fix: a circular buffer, where a "front" pointer just moves forward and wraps around to index 0 once it hits the end, instead of physically shifting data.

Exercise: pick the structure

A print spooler must print documents in the exact order they were submitted. Stack or queue?

Common misconception
"Dequeuing from the front of a JavaScript array (arr.shift()) is fine performance-wise." It works correctly but is O(n) — every remaining element re-indexes. For high-throughput queues, use a circular buffer or a linked-list-backed queue instead.

Key takeaways

  • FIFO: first element enqueued is the first dequeued
  • Naive array-shift dequeue is O(n); circular buffers make it O(1)
  • Queues power task scheduling, print spoolers, and breadth-first search (BFS)

Module 3 Check — Queues

1. What does FIFO stand for?
Correct answer: "First In, First Out" — the earliest-added item is always removed first.
2. Why is naive front-dequeue on a plain array O(n)?
Correct answer: shifting — removing from index 0 forces every other element to move one slot left.
3. What problem does a circular buffer solve for queues?
Correct answer: wrapping the pointer — front/back indices move and wrap around the fixed buffer instead of shifting elements.
4. Which scenario is the best fit for a queue rather than a stack?
Correct answer: serving tickets in arrival order — that's fairness by arrival time, the defining FIFO use case.
MODULE 04 / PRACTICAL MASTERY

Choosing and Combining the Right Structure

Real systems rarely use one structure in isolation. This module is about pattern recognition: given a problem, which structure (or combination) actually fits — and what happens when you get it wrong.

Decision framework

Combined example — undo/redo (two stacks)

An editor's undo/redo is two stacks working together: every edit pushes onto undoStack; pressing undo pops it and pushes the reversed action onto redoStack; a new edit clears redoStack.

function applyEdit(action) {
  undoStack.push(action);
  redoStack.length = 0;   // new edit invalidates redo history
}
function undo() {
  if (!undoStack.length) return;
  const action = undoStack.pop();
  redoStack.push(action);
  // ...reverse the action on the document
}

Combined example — BFS with a queue

Breadth-first search visits the nearest nodes first — exactly a FIFO guarantee. This is why BFS implementations always use a queue, never a stack (that would be DFS instead).

function bfs(startNode) {
  const queue = [startNode], visited = new Set([startNode]);
  while (queue.length) {
    const node = queue.shift(); // dequeue from front
    // process node...
    for (const neighbor of node.neighbors) {
      if (!visited.has(neighbor)) { visited.add(neighbor); queue.push(neighbor); }
    }
  }
}

Exercise: complexity check

A queue is implemented with array.shift() for dequeue, processing 100,000 items. What's the total cost?

Common misconception
"BFS and DFS just differ in traversal order for style reasons." They differ because of the underlying structure: swap a queue for a stack in the exact same traversal loop and you get depth-first behavior instead of breadth-first — same code shape, opposite guarantee.

Key takeaways

  • Random access need → array. Undo/most-recent-first → stack. Fairness/arrival-order → queue.
  • Complex features (undo/redo, BFS) are usually simple combinations of these primitives
  • The wrong structure doesn't always crash your program — it silently produces wrong order

Module 4 Check — Mastery

1. Why does BFS use a queue instead of a stack?
Correct answer: FIFO order visits closer nodes before farther ones, which is the definition of breadth-first.
2. In two-stack undo/redo, what must happen when a new edit is applied?
Correct answer: clear the redo stack — a fresh edit invalidates any "future" you could redo to.
3. You need to look up a user's profile instantly by their numeric ID. Best fit?
Correct answer: Array — direct index lookup is exactly the O(1) random-access strength arrays provide.
4. Repeatedly calling array.shift() to dequeue n items from an n-length array costs:
Correct answer: O(n²) — each shift is O(n) on average, and you do it n times.
